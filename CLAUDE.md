# Inspired Mile — Sonnet Man

Shakespeare rap-battle card game. Live at **sonnetman.inspiredmile.com**.
Astro static site + Rust API (`backend/`, axum + sqlx + Postgres).

## Stack

- Astro 7, Tailwind 4 (`@tailwindcss/vite`; theme lives in `src/styles/global.css`), React 19
- In-browser AI through `@huggingface/transformers` on WebGPU; no server does inference.
  `src/lib/brain.ts` knows three models: Gemma 4 E2B (3.1 GB), LFM3 1.7B (1.1 GB) and
  LFM2.5 350M (295 MB). Which the device can run decides what is offered, and each model
  writes and judges only in the languages it was measured to handle (`writesIn`, `judgesIn`);
  one used in no language is never offered (`modelsToOffer`) and never a fallback when the one
  asked for fails to load (`loadOrder`); a page loads a model on its own only when it is the one
  the visitor chose before and is still offered (`rememberedModel`). Otherwise: the written
  opponent and rule judging.
- Speech: Whisper base on WebAssembly (`src/lib/ear.ts`); Kokoro for English voice.
  The browser's Web Speech recognition is NOT used: it sends audio to a server.
- Babylon.js 9 for the Theatre (`src/lib/xr/theatre.ts`, `/theatre`) and the VR gallery
- Backend: Rust 1.100.0 (pinned in `backend/rust-toolchain.toml`), axum 0.8, sqlx 0.9
- Tests: vitest (pure logic), Playwright (browser), `tests/model` (real models, WebGPU)

## The game

A three-round duel of verses. Rules live in `src/lib/verse/` and are pure and seeded:
`forms.ts` (what a verse must do, checked by code), `devices.ts` (what cards do),
`duel.ts` (scoring: craft + judge), `judge.ts` (how a model's preference is read),
`opponent.ts`, `session.ts` (order of play, shared by every front end).
Read the header comment of `judge.ts` before changing judging: asked "A or B?" outright,
small models answer by position. `scripts/judge-eval.mjs` was the first, English-only measurement;
`scripts/model-eval/` measures every model in every language through the game's own functions.
Graded one verse at a time (the lite tier) a model obeys a line such as "Grade: 5" or "Grade:
five" in the verse (measured with `scripts/grade-injection-eval.mjs`). Three defences on the grade
path, all by structure: the grader never reads a line holding a number, a number word or a judge
word (`judgeLines`; the words are `judge-words.ts`, GENERATED by `scripts/build-judge-words.mjs`
from CLDR and Wiktionary); a round in which either verse has such a line is not graded at all,
the rules decide it (`referee`: a verse of empty lines must not win); and the model decides only
what the rule-based judge splits, by `GRADE_MARGIN` (`boundedByRules`). The compare path
(standard, grand) reads both verses whole: leaving lines out there let a digit in every line empty
a verse, which LFM3 then preferred. Its wording names the duel's language beside the verses, chosen
from seven measured with the real models on labelled pairs in sixteen languages
(`tests/model/judge-compare.spec.ts`): the best mean for both models, but against main's wording a
trade inside the noise, better in some languages and worse in others; LFM3 stays near or below
chance in Spanish, Arabic and Hindi under every wording (docs/language/JUDGE-INJECTION.md). The live checklist tells a lite-tier player (in a language that model judges) which lines the
grader will not read and the word that left each out (`DuelSession.judgeUnread`). Keep all three
if the grade path changes, and measure with `tests/model/grade-injection.spec.ts` and
`tests/model/judge-hide.spec.ts` (real models; results in `docs/language/JUDGE-INJECTION.md`) and
`src/lib/verse/grade-path.test.ts` (stand-in models).

What counts as a copy, a verse or a word is measured, not guessed: `src/lib/verse/review.test.ts`,
`review2.test.ts` and `review3.test.ts` print the measurements every threshold in `duel.ts`
(COPY_THRESHOLD, COPY_COVERAGE*, COPY_LINE_*, OWN_WORDS_PER_LINE) and `text.ts` (MIN_KNOWN_SHARE,
FULL_KNOWN_SHARE, TELLING_PER_LINE, SHORT_TELLING, UNLISTED_SPAN, PHRASE_SPAN) was set from, and assert
them, with the checkers' probes as tests; a run is recorded in `docs/language/RULES-MEASUREMENTS.md`. A
copy is measured from both sides (`copyOf`: how much of the player's verse is the opponent's, and how
much of the opponent's it carries), so words added to every line do not hide one; and line by line
(`copyOf().carry`, `duel.ts carriesLines`: each of the opponent's lines carried into a line of its
own that keeps its rhyme, the same last word or one that rhymes with it; or, when the verse has no
line of its own beyond the other's, nearly whole whatever it ends on, or every line of it with
COPY_LINE_SHARE of its words in order or COPY_LINE_ANY of them in any order), so moving the lines
the way the form allows, swapping each rhyme word for another rhyme, or each line's last word and
one more in a haiku, or its inner words about, does not hide one either. A word the
lexicon lacks counts toward the floor inside a phrase (its line holds a little word, or every word
of it has a capital: a roll call of names) when it can be said (`text.ts sayable`): with a vowel letter, every three letters of it found in a word or a name of
the pronunciation table (`pronounce.ts spellingTrigrams`; a drawn-out letter is also tried once);
without one, a held sound (`HELD_SOUND`: brrr, skrrt, pssst, shhh, hmmm). So "finna", "varlet",
"Mwangi" and "skrrt" count and keyboard mash does not; random letters with a vowel can, as a name
can (`review4.test.ts` MASH-V). In Japanese a katakana word counts beside a word written otherwise,
and in a verse with one line of Japanese or more the dictionary's own katakana words count in a run
of two or more (サッカーボール) or alone; neither tells anything. The rule
judge's wordplay is a count of different telling words over as many lines as both verses have (a
line added past the other's length adds nothing), its flow is rhyme, lines opening on the same
word that carries meaning (not a line that says the one before again: a chant), lines that grow and
even lengths, and its wit is a split unless both verses answered one (an "!" decides nothing). `judge-accuracy.test.ts`
holds it to main's accuracy on labelled pairs in all sixteen languages (`judge-pairs/pairs.json`,
`scripts/judge-pairs.mjs`). Generated data, each from a pinned source with its
sha256 (the script refuses a different file): `confusables.ts` (UTS #39, `build-confusables.mjs`),
`function-words/<lang>.ts` (stopwords-iso, `build-function-words.mjs`, loaded with the pack),
`judge-words.ts` (above), `pron-en.ts` (below), `sound/ipadic/*.dat.gz` (kuromoji 0.1.2's IPADIC cut
to what the engine reads, `scripts/sound/build-ipadic.mjs`; `sound/ipadic.test.ts` requires the same
readings as the full dictionary).

English rhyme and syllables are read from a pronunciation table, not guessed from spelling:
`src/lib/verse/pron-en.ts` is GENERATED from the CMU Pronouncing Dictionary by
`node scripts/build-pronunciation.mjs` (run it on the build host with `rb --pull`; the 3.6 MB
dictionary is downloaded there and never committed; it is pinned to one cmudict commit and its
sha256; names it lacks go in `scripts/pronunciation-extra.txt`; a `*` marks a word the
dictionary only spells out, and a `^` one that SCOWL's word lists (pinned release and sha256, in
the same script) do not hold, a name, an abbreviation or a fragment: the substance floor counts
neither as a word). `pronounce.ts` loads it on demand, so it is a chunk of its
own (1.46 MB; 0.56 MB gzip, 0.47 MB brotli) and never in a page's first load; the licence
notice is the data's first lines (`#`), since a build strips comments; `DuelSession.beginRound`
awaits it (through `loadSound(lang)`, which loads every language's data) and the battle page
fetches it only when an English duel is about to start (`battle.astro warm()`: the language picked,
the duel's settings touched, the start button pointed at, or a duel language stored from an earlier
visit or named by `?lang=` once the page is idle; `tests/battle-bytes.spec.ts`); unit tests must
`await loadPronunciation()` first. Both duel
screens draw a `DuelSession`; do not score a round anywhere else.

## Online play (multiplayer)

The SERVER decides every online score, with no model and no randomness: `backend/src/verse/`
is a Rust port of `src/lib/verse/` (English; craft plus the rule-based judge), and
`backend/src/multiplayer/game_room.rs` runs the match (server draws the seed and three
forms; both players write under the same form; best of three). The page
(`src/pages/multiplayer.astro`) previews with the TypeScript rules and recomputes every
round the server sends (`auditRound` in `src/lib/multiplayer-client.ts`). The online round
itself (what "answers" what when both write at once) is `src/lib/multiplayer-rules.ts`.

The two engines are held together by golden vectors. After ANY change to `src/lib/verse/`,
`src/lib/cards.ts` or `src/lib/multiplayer-rules.ts`:

```bash
~/kani-logs/remote/rb --pull . -- "$RB npm ci && scripts/gen-verse-golden.sh"   # rewrites backend/data, backend/tests/golden
~/kani-logs/remote/rb . -- "$RB cd backend && cargo test --release"            # tests/verse_parity.rs must pass
```

`npx vitest run` fails while those files are stale. If the parity test fails, fix the Rust;
never loosen the comparison. Online play has no relics, potions or ink yet.

**Online duels are English only, by decision** (2026-11-17). The server's engine is the English
path; the other fifteen languages are read by sound tables, kuromoji (Japanese) and the
browser's word segmenter (Chinese, Thai), which a Rust server could not reproduce exactly, and a
server that scored them differently from the preview would be worse than none. The page says
so (`#mp-english-only`), `join_room` carries `lang` and the room refuses any language but
`en` (`language_not_offered`). Solo duels stay in all sixteen.

The data both engines read is ONE file each, compiled into the API as text, so the binary must
be rebuilt when any changes: the pronunciation table `src/lib/verse/pron-en.ts`
(`backend/src/verse/pronounce.rs`), Unicode's confusable letters `src/lib/verse/confusables.ts`
(`text.rs`), and the generated `backend/data/cards.json` and `backend/data/english.json`. Every
number is compared as the double it is (serde_json `float_roundtrip`).

The server's Unicode tables (the `regex` crate: Unicode 16) can be older than the browser's
(Node 26 and current Chrome: 17). A verse holding a character the server does not assign is
refused (`unknown_character`) rather than scored differently from the preview; the page lets
the player edit and resend. Browsers with OLDER tables than the server (an old Safari) are not
covered by this and were not tested: the page's audit says so when a round disagrees.

`cleanVerse` now repeats itself until nothing changes, but online play still SETTLES a verse
(`settleVerse` / `settle_verse`): the page previews and sends the settled text and the room
settles what arrives. Preview the textarea through `previewCraft`, never `onlineCraft` of the
raw text. The single-player page previews `DuelSession.preview()` of the same text `submit()`
scores (`src/lib/battle-preview.test.ts`).

What the room enforces besides the rules: three to five characters, each a starter character
(`ONLINE_STARTER`: the first three of the catalogue) or one the account's `owned_cards` holds
(`handlers.rs not_held`; the collection is otherwise the browser's, so this binds a deck to
what the account records, not to what a player paid for); at most `MAX_ROOMS_PER_USER` live
rooms per account and `MAX_ROOMS_PER_ADDRESS` (40) per network (an IPv4 address or an IPv6 /48:
`handlers.rs origin_of`, the client address as every other limit finds it, `auth::client_addr`,
so a forwarding header counts only from `TRUSTED_PROXIES` and with `PROXY_SECRET` when it is
set), counted over every room (a busy room is waited for, never skipped) and opened
one at a time (`RoomManager::open_room`). A limit is the business of the player who reached it:
a quick-match player who reaches one while waiting is told so (429) and leaves the queue, and the
requester is paired with the next player or waits (`matchmaking.rs`). A quick-match room whose
second player does not arrive within `Timing::arrival` (60 s, from the pairing) closes with
`opponent_absent`, and so does a private room where a friend waits that long for an inviter who
is away. The page stops asking for a quick match after `QUICK_MATCH_LIMIT_MS` (3 min) and says
so. Nobody is paired with a player who has gone: every request runs to its end
(`backend/src/request_task.rs`, so a transaction is never cut off part-way), but a request is
told when its client has gone (`ClientGone`), and a quick-match request then gives up its place;
the page also leaves the queue on `beforeunload` and `pagehide` (a keepalive `DELETE /queue`,
sent BEFORE the waiting request is aborted: with the service worker in control, Chromium never
delivered one sent after the abort), for a proxy that does not pass the close on. Only a handler that holds no transaction may stop early on
`ClientGone`. A reconnect keeps the verse being written and the character chosen while the round is the
same; the client keeps trying for `RECONNECT_WINDOW_MS` (60 s, longer than the 45 s grace); a
reload, a visit to another page or a back/forward-cache restore (`pageshow`) takes the seat back
(the tab keeps it in sessionStorage, `inspired-mile-mp-seat`, with the draft); a returning player
is not checked for cards again; a new tab offers "Return to your duel" (`/rooms`), and leaving
mid-match asks first (beforeunload).

How long the server keeps a battle's verses is a published promise (privacy.astro: "for up to
two minutes after it ends"). A finished room answers a returning player for `Timing::linger`
(90 s); after that it is `gone()`: it takes nobody, is not listed, and the next sweep
(`SWEEP_EVERY`, 15 s) empties it (`retire`: the verses are dropped even while a timer still
holds the room) and removes it. The build itself (a const assertion in game_room.rs) holds
`FINISHED_LINGER + SWEEP_EVERY <= POLICY_AFTER_THE_END` (120 s), and
src/lib/privacy-retention.test.ts holds the policy's words to `POLICY_AFTER_THE_END`. Change any
of these and the policy together.

## Building the API

The API compiles in files the browser also reads, so it is built inside the whole repository,
never from `backend/` alone (the old `backend/Dockerfile`, which copied `backend/src` only, is
gone; there is no container image). It needs exactly: every tracked file under `backend/`,
`src/lib/verse/pron-en.ts` and `src/lib/verse/confusables.ts`. `scripts/check-api-build.sh`
builds from a clean copy of just those (`cargo build --release --locked`) and is the proof the
list is complete. A deploy copies the binary and `backend/migrations/` (read at start-up from
the working directory) to prod; see "Where it runs".

## Build and test — on the build host, never on the dev Mac

```bash
RB='export PATH=$HOME/.cargo/bin:/opt/homebrew/bin:$PATH;'
~/kani-logs/remote/rb . -- "$RB npm ci && npx vitest run && npm run build && npx playwright test"
~/kani-logs/remote/rb . -- "$RB cd backend && cargo test --release && cargo build --release"
# real models in a WebGPU browser (the build host's headless Chromium has Metal); downloads up to 3 GB
~/kani-logs/remote/rb . -- "$RB TIERS=lite,standard,grand npx playwright test -c playwright.model.config.ts"
# after a deploy:
~/kani-logs/remote/rb . -- "$RB PROD_URL=https://sonnetman.inspiredmile.com npx playwright test"
```

The frontend build needs no secrets or `PUBLIC_*` variables.

Do not start a second `rb` in this checkout while one is running: both use the same remote
folder.

`npx playwright test` starts three things itself (`playwright.config.ts`): a throwaway
Postgres and two copies of the real API (`tests/start-backend.sh`; needs `initdb`, `pg_ctl`,
`createdb` and `cargo` on `PATH`, hence `/opt/homebrew/bin` and `~/.cargo/bin` above), and
the Astro dev server, which proxies `/api` to the API (`astro.config.mjs`). State and logs
go to `.e2e/` (git-ignored); the sign-in codes the tests read are in `.e2e/api.log`.

**The build host is shared, and no server is reused.** Default ports: 4399 (dev server),
38490 (API, `DEV_EMAIL_LOG=1`), 38491 (API with email off), 54329 (Postgres). If another
checkout is testing at the same time the run stops with "port already used"; give this run
its own with `E2E_WEB_PORT`, `E2E_API_PORT`, `E2E_API_NOEMAIL_PORT`, `E2E_PG_PORT`
(`tests/e2e-env.ts`). Before 2026-11-16 the config reused whatever answered on 4399, so two
concurrent runs could test each other's code and pass.

**Never `pkill -f 'astro dev'` on the host.** It stops every checkout's dev server, not
only a stale one of yours: a run in another checkout then fails with "connection refused"
on all its browser tests (its log says `[dev-server] EXITED with status 143`). A dev server
left behind by a killed run is found by its port: `lsof -nP -iTCP:<port> -sTCP:LISTEN`.

## Sign-in (passkeys + email code)

- No passwords, no Google. Passkeys (WebAuthn, discoverable, no username) are primary; a
  6-digit emailed code creates an account, signs in where there is no passkey, and recovers.
  Code: `backend/src/auth/`, `src/lib/passwordless.ts`, the auth script in `BaseLayout.astro`
  (all its strings are in one `STRINGS` object).
- **Sessions live on the server** (`auth_sessions`, `backend/src/auth/sessions.rs`). The cookie
  holds a JWT whose `sid` names a row; a request is signed in only while that row is live.
  Sign-out revokes the row, `POST /auth/logout/all` revokes all of the account's. Every check
  reads one condition (`sessions.rs live_session!`). The game's WebSocket outlives the request
  that opened it, so it checks its row again before it acts on a message (a seat, a verse, a
  forfeit; a message that can do nothing costs no lookup, and an answer is good for
  `SESSION_FRESH_FOR`, 1 s) and every `SESSION_CHECK_EVERY` (15 s) while in a room, and closes
  with `signed_out` once the row is gone (`multiplayer/handlers.rs SessionGate`; a database that
  cannot be asked within 3 s is not taken for a sign-out, so an outage does not cost a match). A
  quick-match request checks its partner's row before answering "matched": a player who signed
  out while waiting is not paired (`join_queue`). The cookie is
  `__Host-im_token` when every `WEBAUTHN_ORIGIN` is https (production) and `im_token` over
  http (localhost, tests: browsers refuse the prefix there); HttpOnly, Secure, SameSite=Strict.
- **Adding or removing a passkey, and adding an email, need a fresh proof** (a passkey
  assertion or an emailed code in the last 5 minutes), not just the cookie. The page gets
  403 `reauth_required`, runs `/auth/passkey/verify/{begin,finish}` and retries
  (`withFreshProof` in `passwordless.ts`).
- **`JWT_SECRET` is mandatory**: the API exits at start-up if it is absent, under 32 bytes,
  or the old development constant. `DEV_INSECURE_JWT_SECRET=1` lifts that on localhost only
  (refused with an https origin). Email codes use a key derived from it, not the secret itself.
- API env: `WEBAUTHN_RP_ID` (default `inspiredmile.com`; **never change it once passkeys
  exist, it orphans all of them**), `WEBAUTHN_ORIGIN` (default
  `https://sonnetman.inspiredmile.com`; comma-separated list; each must be https, or http on
  localhost, and on the RP ID), `RESEND_API_KEY` (absent: email endpoints answer 503 and
  the UI hides email), `EMAIL_FROM`, `RATE_LIMIT_PER_MINUTE` (per client, default 600),
  `TRUSTED_PROXIES` (peers whose `CF-Connecting-IP` / `X-Forwarded-For` are believed; default
  `127.0.0.1,::1,10.10.10.1,100.64.224.0,100.98.101.113`. The last is the Tailscale address of
  the M4 MacBook Pro (10.10.10.1): its Caddy reaches the API on prod at `100.64.224.0:3849` over
  the tailnet, so that is the peer production sees (checked 2026-11-16). From any other peer the
  socket address is the client. **Check this on every deploy**, in the API log: whatever
  `RUST_LOG` says (even `off`), the API writes at start-up `TRUSTED_PROXIES: ... believed only
  from <list>`, and, at most once every ten minutes per peer and ten lines a minute,
  `ignored CF-Connecting-IP / X-Forwarded-For from <peer>`. If that peer is the proxy, add it:
  otherwise every visitor shares one allowance. These are "operator notices"
  (`backend/src/notice.rs`): the log filter is `RUST_LOG` with a directive for that target
  added last; the log has no colour codes unless standard output is a terminal),
  `PROXY_SECRET` (optional, 32+ characters: when set, a trusted peer's forwarding headers are
  believed only on requests carrying it as `X-Proxy-Secret`, which every proxying Caddy must
  add with `header_up`; the proxy's host is a shared build host, so without it any program
  there can choose the address it is counted as),
  `SIGNUP_GLOBAL_PER_HOUR` (default 300; logs `SIGN-UP CEILING HIT`),
  `SIGNUP_BEGINS_GLOBAL_PER_HOUR` (default 1500 begun sign-ups an hour, site-wide; logs
  `SIGN-UP BEGIN CEILING HIT`), `AUTH_CHALLENGES_MAX` (default 50000 rows in `auth_challenges`;
  one network may hold 300 live; logs `SIGN-IN CHALLENGE CEILING HIT`),
  `UNUSED_ACCOUNT_PURGE_DAYS` (default 30, 0 = never: passkey-only accounts that never played
  are deleted, see `purge_unused_accounts` in `auth/passkeys.rs`).
- **A site-wide ceiling never refuses everyone** (`auth/passkeys.rs`, top). At one, only a
  network that has already had a small share is refused: 2 accounts or 10 begun sign-ups in the
  hour, or 10 live sign-in ceremonies; everyone else is served. Before 2026-11-16 (second
  review) a full challenge table refused every visitor, so one IPv6 /48 split into 200 /64s
  stopped all passkey sign-in in nine seconds. Do not bring back a ceiling that refuses all.
- Limits are per network, never per address, at three widths (`auth/client_ip.rs`, top): the
  request rate limit per IPv4 address or IPv6 /64; everything one party could turn on another
  or use to fill a table (email codes and guesses, sign-in ceremonies, game rooms) per IPv4
  address or IPv6 /48, because one home line holds 256 or 65,536 /64s; the sign-up budget (40 accounts an
  hour, counted when created) per IPv4 /24 or IPv6 /48.
- Email codes (`backend/src/auth/email_code.rs`, top comment, is the statement): an inbox (the
  address without its `+tag`, and for Gmail without dots) gets at most 10 codes an hour; one
  network (IPv4 address or IPv6 /48) may have at most 3 of them, so no network, and no three
  together, can stop another from getting a code; it takes four. Wrong guesses: 10 a day per
  network per address, 50 per address from everyone, 30 per network over all addresses (a miss
  is forgiven for that last count once the same network signs in with a code for the
  address). All checked under the inbox's and the network's advisory locks in the transaction
  that inserts, so parallel requests cannot pass them.
- `TEST_ONLY_LIMIT_RACE_DELAY_MS` pauses between each limit's check and its write, so the
  end-to-end tests can show a check made without its lock letting parallel requests through.
  The API refuses to start with it when any `WEBAUTHN_ORIGIN` is https. Never set it in a
  deployed `.env`.
- **Accounts that exist only by email cannot sign in while email is off** (no `RESEND_API_KEY`):
  an old Google or email account has no passkey and its only way in answers 503. Production
  had no users when this was accepted (2026-11-16); the sign-in panel says so. Check
  `SELECT COUNT(*) FROM users u WHERE NOT EXISTS (SELECT 1 FROM webauthn_credentials c WHERE c.user_id = u.id)`
  before relying on it.
- `DEV_EMAIL_LOG=1` writes codes to stderr instead of sending. Tests only. A real key wins
  over it, with a loud start-up warning.
- Local dev: `WEBAUTHN_RP_ID=localhost WEBAUTHN_ORIGIN=http://localhost:4321`.
- The email step requires the age gate's stored tier (`adult` or `teen-consented`), in the
  browser and again in the API. Do not loosen either. The tier is self-declared (nobody's
  age is verified). Rules in `backend/src/auth/age.rs`: set at account creation; afterwards
  only the signed-in user's own answer changes it (the age question opened by "Date of Birth"
  in the account menu, `POST /auth/age-tier`). The page never posts the browser's stored gate
  answer by itself (on a shared browser it may be someone else's), and `/credits/age-verify`,
  which pages cached before 2026-11-16 still call, never writes. Adult may become teen; teen
  becomes adult again only for an account declared adult, with a proof from the last five
  minutes; an account declared teen stays teen (the operator can change it in the database).

## Languages (16: en es fr de it pt pl ru ar hi zh ja ko vi th id)

- **Interface**: `src/i18n/` (`t()`, `setLocale()`, one lazily loaded module per language in
  `locales/`). Markup carries keys (`data-i18n`, `data-i18n-placeholder`, …); scripts call
  `t()` and redraw on `onLocaleChange`. A new string goes into `locales/en.ts` and all fifteen
  others: `src/i18n/i18n.test.ts` fails on a missing key, an empty value or a different
  `{placeholder}`. Translated so far: the layout (navigation, footer, age gate, sign-in), the
  battle page and the theatre. Card names and Shakespeare's lines stay English.
- **The duel's language** is a separate choice. The engine (`src/lib/verse`) returns message
  keys, never sentences; `english.ts` renders them for the model's prompt, which is always
  English. Per-language data (acrostic words, forbidden letters, power words, the written
  opponent's verses) is in `src/lib/verse/packs/`, loaded with `loadPack(lang)` before
  `createDuel`. Rhyme and syllable rules per language: `rhyme.ts`, `text.ts`; thresholds:
  `lang.ts`.
- **Rhyme and syllables go by sound**, not spelling, where the spelling does not show it:
  `src/lib/verse/sound/` holds one lazily loaded table per language (stress, pronunciation,
  character readings; built by `scripts/sound/build.mjs` from Wiktionary, Unihan and
  CC-CEDICT) and a Japanese analyser (kuromoji, with its dictionary cut to what the engine reads:
  `sound/ipadic`, 4.7 MB compressed and 16 MB unpacked where kuromoji's own was 17.8 and 100;
  rebuild with `node scripts/sound/build-ipadic.mjs` after `npm ci`). `loadSound(lang)` goes beside
  `loadPack(lang)` before `createDuel`; the battle page also starts it ahead of the duel when the
  visitor shows they are about to play (`battle.astro warm()`, above), so a Japanese duel need not
  wait for the dictionary when it starts. A first visitor who leaves the duel's settings alone
  fetches none of it, and one who starts at once still waits for it (about 5 s on a throttled
  phone: `tests/battle-ja-cost.spec.ts`). Chinese, Japanese and Thai offer rhyming forms only
  once their data is loaded; Arabic and Thai offer no syllable forms. Sources, licences,
  measured accuracy and how to rebuild: `docs/language/PHONETICS.md`. After changing a rule
  or a table, run `scripts/sound/measure.mjs --write` (it records the digests the unit and
  browser tests must reproduce). `node scripts/sound/mutate-sound.mjs` (build host) proves
  those tests go red.
- **The test sets mostly come from the dictionaries the tables are built from**, so they
  cannot show a table's faults. `sound/corpus/espeak.json` can: common words and their
  phonemes from espeak-ng, which shares no data with the tables. After rebuilding a table,
  run `scripts/sound/crosscheck.mjs --show 40` and read the disagreements. It found, on
  2026-11-16, that the build had let one transcription stand for a word: Wiktionary lists
  several per word (careful, casual, regional) in no useful order, so never take the first.
- **Where a model is used is measured, not assumed** (`docs/language/MODEL-EVAL.md`).
  `MODELS[tier].writesIn` / `.judgesIn` in `src/lib/brain.ts` list the languages in which each
  model writes the opponent's verse and judges; anywhere else the written opponent plays and the
  rules judge, and the language picker on the battle page says so (with a model loaded it lists
  the languages under two headings, who writes there, and a note under it says why). The lists are copied from
  `docs/language/model-eval/decisions.json`, which `scripts/model-eval/analyze.mjs` derives from
  the result files in `docs/language/model-eval/cells/` by the thresholds in
  `scripts/model-eval/thresholds.json`; `src/lib/model-eval.test.ts` fails when either drifts.
  Never edit a list by hand: run the cell again (`scripts/model-eval/run.mjs`, on the build host,
  one run at a time, under memguard; it resumes), then `analyze.mjs`, then `copy-lists.mjs`.
  A language with no result file is unsupported for that model. The test "every writing cell
  replays…" re-runs the game's code over each stored draft and fails when the rules or the
  opponent's prompt changed after the cells ran; `src/lib/model-eval.judge.test.ts` fails when
  the judge's prompts differ from the fingerprint each judging cell carries, and when the gate in
  `referee.ts`/`session.ts` (model only in its listed languages) is lost in a merge. After a
  rule change (forms, devices, rhyme, syllables, the tidy-up):
  `MEVAL_RESCORE=1 npx vitest run src/lib/model-eval.rescore.test.ts` scores the stored drafts
  again (no model), cell by cell, then `analyze.mjs` and `copy-lists.mjs`. A cell it cannot
  re-score (its prompt changed, or the duel now draws other forms) needs the model: run it again,
  or meanwhile add `MEVAL_SET_ASIDE=1` to move it to `docs/language/model-eval/set-aside/`, where
  it counts as not measured (a cell of that name set aside before is kept, moved to
  `set-aside/before-<day>/`: `src/lib/model-eval-aside.ts`). The same variable with `model-eval.judge.test.ts` sets aside judging
  cells whose prompts changed. `run.mjs` measures set-aside cells again. New cells: copy them into
  `cells/`, then `node scripts/model-eval/judge-code.mjs` (git only) and
  `MEVAL_FINGERPRINT=1 npx vitest run src/lib/model-eval.judge.test.ts` before `analyze.mjs`.
  Each judged pair also keeps the model's raw reading (`referee.ts JudgeReading`), and
  "every verdict follows from the reading…" derives each stored verdict again with the code now,
  so a change to how an answer is read (`SPLIT_BELOW`, `GRADE_MARGIN`, `combineMargins`,
  `boundedByRules`, and the rules' split that bounds the grade path, `referee.ts rulesSplit`, which the
  test calls itself) turns it red as a prompt change turns the fingerprint red.
  `node scripts/model-eval/mutate-gates.mjs` (build host) proves the gates, the pages' lines
  (badge, note, verdict, theatre), the loading rules and the reading are all held by a test;
  the page tests use a stand-in model library (`tests/stand-in-model.ts`).
  The replay, the re-score and `run.mjs` load a language's sound data (`src/lib/verse/sound`,
  from the phonetics work) wherever the game does.
- Every verse in every pack must keep its form as the code checks it (`verse.test.ts`).
  `node scripts/mutate-packs.mjs` (on the build host) proves those tests go red.
- Writing a `\uXXXX` escape through an agent's file tools can turn it into the character
  itself; check with `grep` after writing one.

## Where it runs (verified 2026-11-16)

- **Live origin for the domain is `10.10.10.1`**: Cloudflare's "publishing" tunnel terminates
  there, not on prod. Its Caddy serves `~/sites/inspired-mile-web` and forwards `/api/*`
  (including the multiplayer WebSocket) to prod at `100.64.224.0:3849`.
- **Static build is mirrored to both** `10.10.10.1` and prod (`100.64.224.0`), same path.
  Sync with `rsync --delete --exclude=.git/`.
- **API on prod**: `~/sites/inspired-mile-api/` (binary, `migrations/`, `.env`), launchd
  `com.inspiredmile.api`, logs `~/sites/logs/inspiredmile-api*.log`, Postgres 18 database
  `inspired_mile`. It lives outside the web root on purpose: `.env` must never be servable.
  `DATABASE_URL` needs an explicit user (sqlx 0.9 no longer infers it). Migrations are read
  from `./migrations` at start-up, so sync that folder with the binary.
- Replace the binary by writing a new file and renaming it, then
  `launchctl bootout` + `bootstrap` (not an in-place copy). Prod is arm64 macOS: build the
  release binary on an Apple Silicon build host (the Studio, or the M4), never the Intel iMac.
- **Before swapping the binary**, run `scripts/check-migrations.sh <the new migrations folder>
  -d inspired_mile` on prod (any psql connection arguments after the folder). It compares
  `_sqlx_migrations` with the files the way sqlx does (SHA-384 of each file) and exits 1 when the
  new API would refuse to start: a migration changed after it was applied (`VersionMismatch`), an
  applied one left out (`VersionMissing`), or one that failed half-way (`Dirty`).
- **Rolling back keeps the newer migrations.** sqlx refuses to start when the database has a
  migration its folder lacks (`VersionMissing`), so to go back to an older binary, put the old
  binary in place and leave `./migrations` as it is (every migration here only adds, and keeps
  the old binary working). Never delete an applied migration file.

## Gotchas

- `@tailwindcss/upgrade` rewrites plain words in data files as classes ("a ring" became
  "a ring-3"). Diff `src/lib/*.ts` after running it.
- The stylesheet is imported once, in `BaseLayout.astro`. Do not import it per page.
- The age gate covers every page until a date of birth is stored; tests start past it
  (the `storageState` in `playwright.config.ts`).
- No GitHub Actions (account-wide owner rule). CI is the build host.
- `git add -A` here will pick up agent worktrees under `.claude/`; that folder is ignored.
- Babylon's default WebXR set-up downloads hand and controller models from its own
  servers; `theatre.ts` turns that off, and a test asserts no foreign request in a session.
- To test WebXR under emulation, delete `Navigator.prototype.xr` before installing `iwer`.
- The theatre's panels break lines between words as `Intl.Segmenter` finds them, and keep the
  line-break rules of Japanese and Chinese (no closing punctuation opens a line, no opening
  bracket ends one) and Thai's ๆ and ฯ: `src/lib/xr/line-break.ts`, checked on what Babylon drew
  in `tests/theatre.spec.ts`.

## Requests to other origins (the privacy policy depends on this)

The policy (`src/pages/privacy.astro`, "Other Companies Involved") tells visitors exactly
which other companies their browser talks to. `tests/third-party.spec.ts` loads every page in
every age-gate state and fails on a request that `tests/third-party-allowlist.ts` does not
list. Add a third-party request only by adding it to that file **and** to the policy.

- A page may fetch from another origin only: the Plausible script (after the age gate is
  passed, never before and never for a blocked visitor: `window.__loadAnalytics` in
  `BaseLayout.astro`), and model weights from the Hugging Face hub when a model is asked for.
- Libraries default to public CDNs; each default is overridden, and the files are shipped
  from this site by `scripts/self-hosted-runtime.mjs` (an Astro integration: served by a
  middleware in dev, copied to `dist/ort/` and `dist/vendor/` in a build, about 90 MB):
  - Transformers.js takes onnxruntime-web's `.wasm`/`.mjs` from cdn.jsdelivr.net. Import it
    only through `loadTransformers()` (`src/lib/model-runtime.ts`), never directly.
  - kokoro-js carries its own Transformers.js 3; `thespian-voice.ts` sets `env.wasmPaths`.
  - model-viewer takes Draco/KTX2 decoders from www.gstatic.com. Load it only through
    `loadModelViewer()` (`src/lib/ar-viewer.ts`), never with a script tag.
  - Babylon WebXR: both `theatre.ts` and `vr-engine.ts` turn off hand tracking, near
    interaction and online controller models (they come from Babylon's servers).
- An upgrade of any of these libraries can move the files: the integration then stops the
  build, and the tests show what the browser asks for.
- `tests/warm-up.ts` (Playwright `globalSetup`) opens every page once before the tests
  start, so the dev server's cold compile is not inside any test's 30 seconds. Without it
  the first tests of a run sat at 15 to 26 seconds on main, and timed out with one more spec.
- The two "model runtime" tests download Whisper and Kokoro (about 80 MB each) from the hub;
  `E2E_NO_DOWNLOADS=1` skips them. `playwright.model.config.ts` takes its port from
  `E2E_WEB_PORT` like the main config.
